# OLNOO Insurance — Project Rules

## 1. Главное правило

НЕ УСЛОЖНЯТЬ.

Всегда сначала искать самый простой, прямой и надёжный способ решения задачи.

Не создавать новый сервис, сервер, базу данных, архитектурный слой или абстракцию, если существующая структура нормально решает задачу.

---

## 2. Одна универсальная платформа

OLNOO Insurance — одна страховая платформа.

Sport, Travel, Auto, Property, Health, Business и будущие направления являются продуктовыми модулями одной платформы.

Не создавать независимый backend и независимую клиентскую базу для каждого страхового направления.

---

## 3. Person — единый человек

Каждый реальный человек получает постоянный внутренний `person_id` OLNOO.

Спортсмен, путешественник, автовладелец и клиент других страховых продуктов — это один Person.

Нельзя создавать нового Person только потому, что человек пришёл из другого продукта или партнёра.

---

## 4. Внешние ID

ID внешних систем нельзя использовать как основной OLNOO ID.

Например:

`athlete_id` федерации → external_identity → OLNOO person_id.

Все внешние идентификаторы хранятся через универсальную связь external identity.

---

## 5. Общие модули переиспользуются

Следующие функции должны быть общими для всех страховых продуктов:

- payments;
- documents;
- OCR;
- policy generation;
- notifications;
- storage;
- authentication;
- audit;
- analytics.

Не создавать отдельный payment-модуль или OCR под каждый продукт.

---

## 6. Интеграции через connectors/adapters

Федерации, брокеры, страховые компании, платежные системы и другие внешние системы подключаются через отдельные adapters/connectors.

Core не должен содержать логику конкретного партнёра.

Запрещён подход:

`if federation == ...`

в универсальном Core.

---

## 7. Один backend на первом этапе

На первом этапе используется один модульный backend OLNOO Insurance.

Не создавать микросервисы без объективной необходимости.

Тяжёлые или специализированные сервисы могут существовать отдельно, например OCR и AI Router.

---

## 8. Одна универсальная база

Используется одна модель PostgreSQL для платформы.

Не создавать:

- sport_db;
- travel_db;
- auto_db;
- property_db.

Различия между продуктами реализуются через product modules и связанные данные.

---

## 9. Документация — часть архитектуры

Если меняется:

- архитектура;
- структура БД;
- продуктовая модель;
- интеграционный контракт;
- политика безопасности;

соответствующий документ должен быть обновлён.

---

## 10. Не менять архитектуру молча

Перед крупным архитектурным изменением:

1. определить проблему;
2. проверить существующую структуру;
3. проверить самый простой вариант;
4. объяснить необходимость изменения;
5. получить подтверждение;
6. только потом менять архитектуру и код.

---

## 11. Минимальные изменения

Не менять соседние модули, страницы и сервисы без необходимости.

Точечная задача должна решаться точечным изменением.

---

## 12. Production

Production не используется как экспериментальная среда.

Основной рабочий процесс:

GitHub → изменение проекта → проверка → GitHub → server pull/build/restart.

Секреты и production-конфигурация могут храниться только в защищённых server environment files.

---

## 13. Персональные данные

Не передавать и не сохранять персональные данные сверх необходимого.

Не писать паспортные данные, номера документов и содержимое документов в обычные технические логи.

---

## 14. Приоритет документов

При конфликте:

1. PROJECT_RULES.md
2. ARCHITECTURE.md
3. DATABASE.md
4. PRODUCT_MODEL.md
5. SECURITY.md
6. документация конкретного модуля
7. текущий код

Если документация и код расходятся, необходимо определить актуальное состояние и привести их к одному виду.

---

## 15. Основной принцип

OLNOO Insurance:

1 Core  
1 Person model  
1 universal database  
1 modular backend  
many insurance products  
many partners  
many connectors  
reusable modules
